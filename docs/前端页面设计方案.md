## 4. 核心交互规则（必写）

### 4.1 Token 存储策略

| Token | 存储位置 | 说明 |
|---|---|---|
| accessToken | **Pinia 内存（不持久化）** | 防 XSS 持久窃取；页面刷新后通过 refresh 重新获取 |
| refreshToken | **后端 HttpOnly Cookie** | 前端不读写；Axios `withCredentials: true` 自动携带 |

> **「记住我」语义**（§3.1 登录表单）：勾选 → 后端设置 refreshToken Cookie 时带 `Max-Age=7天`（跨浏览器重启保持登录）；不勾选 → session Cookie（关闭浏览器即过期）。两种情况下 refreshToken JWT 内部均限 7 天有效，语义自洽。

### 4.2 Axios 拦截器（utils/request.ts）

**请求拦截器：**
- 若 Pinia.user.accessToken 存在 → `config.headers.Authorization = Bearer ${accessToken}`
- `config.withCredentials = true`（携带 HttpOnly Cookie）

**响应拦截器：**
- 正常 2xx + `Result.code === 200` → `return Promise.resolve(data.data)`
- `code === 2002`（乐观锁冲突）→ `ElMessage.error('该账目已被其他操作修改，请刷新页面重试')` → reject
- `code === 500/2001/其他业务错误` → `ElMessage.error(data.msg)` → reject
- **HTTP 401 或 `code === 401`**（无感刷新）：
  1. 若已有 refresh 请求在飞 → 当前失败请求塞进 pending 队列，返回新 Promise
  2. 若无锁 → 加锁 → `POST /api/auth/refresh`（带 Cookie，不需 body）
     - 成功 → 更新 Pinia accessToken → 重放 pending 队列所有请求（用新 token）
     - 失败 → 清空 Pinia → `ElMessage.warning('登录已过期，请重新登录')` → `router.push('/login?redirect=' + 当前path)` → 队列全部 reject
  3. 解锁

**下载类接口特殊处理：**
- `responseType: 'blob'` 的请求 → 不进 code 拦截器，返回响应对象本身
- `parseFilenameFromDisposition(header)` 解析 `filename*=utf-8''...` 中文文件名

### 4.3 路由守卫（router/guards.ts）

```
beforeEach(to, from, next):
  1. whiteList = ['/login', '/404']，命中 → next()
  2. Pinia.user.accessToken 存在 → 已登录访问 /login 则 next('/dashboard')，其他 next()
  3. accessToken 不存在（刷新/首次）→ 调 authApi.refreshToken()
     - 成功 → 写入 Pinia → next(to.path)
     - 失败 → next('/login?redirect=' + encodeURIComponent(to.fullPath))
  4. 登录成功后从 redirect query 取值跳转
```

### 4.4 跨月修改二次确认

- 编辑模式下，保存前对比 `原 accountDate.month` 与 `新 accountDate.month`（跨年也算）
- 不同 → `ElMessageBox.confirm('跨月修改将重置本月及上月的预算进度缓存与仪表盘缓存，是否继续？', '提示', {type:'warning'})` → 确认才 PUT /update

### 4.5 修改密码（新增功能，依赖后端补接口）

- 入口：顶栏头像下拉 → 「修改密码」→ ModifyPasswordDialog
- 表单字段：旧密码 / 新密码 / 确认新密码（新密码强度复用注册规则：6-100 位）
- 提交：`PUT /api/user/password`，body `{ oldPassword, newPassword }`（后端校验旧密码，失败返回错误码 1006）
- 成功后后端 `token_version` 自增 → 所有旧 Token（含当前会话）失效
- 前端收到成功后：清空 Pinia user store → `ElMessage.success('密码已修改，请重新登录')` → `router.push('/login')`
- **跨端依赖**：该接口后端目前不存在，需后端在 HLD/详细设计中补 U-XX 并实现，否则无法联调（见 §8 风险表）

## 5. 环境变量

| 文件 | 变量 | 值 | 说明 |
|---|---|---|---|
| `.env.development` | VITE_API_BASE_URL | `/api` | 结合 `vite.config.ts` 的 `server.proxy./api.target = http://localhost:8080; changeOrigin: true`，本地无跨域 |
| `.env.production` | VITE_API_BASE_URL | `""`（空） | 与前端同域部署，Nginx 反代 `/api` 到后端容器 |

> **说明**：不写死 `http://localhost:8080` 是因为生产环境前端与后端不同域时会导致 Cookie SameSite 问题。开发走 proxy `/api`，生产走同域 Nginx 反代，是业界最佳实践。

## 6. 后端接口字段对应（types/api.ts）

### 6.1 通用响应

```typescript
interface Result<T> {
  code: number;      // 200=成功, 401=未授权, 2001=业务错误, 2002=乐观锁冲突
  msg: string;
  data: T;
}
```

### 6.2 用户模块

| 接口 | 方法 | 路径 | 请求体 | 响应体 |
|---|---|---|---|---|
| 注册 | POST | /api/user/register | `{ username, password }` | void |
| 登录 | POST | /api/user/login | `{ username, password }` | `{ accessToken, userInfo: { id, username, nickname } }` |
| 获取信息 | GET | /api/user/info | — | `{ id, username, nickname }` |
| 修改密码 | PUT | /api/user/password | `{ oldPassword, newPassword }` | void |

## 8. 风险与假设

| 项 | 内容 | 建议 |
|---|---|---|
| CORS/HttpOnly Cookie | 开发环境前端 5173、后端 8080，refreshToken 需 Set-Cookie | 强制开发走 `server.proxy /api`；后端 CorsConfig 开发配置 `allowed-origin-patterns: http://localhost:5173` + `allow-credentials: true` |
| 分类字典一致性 | 后端 category 是纯 String，前端字典名必须与历史数据一致 | `types/business.ts` 字典与接口测试文档 §2.5 A-01 测试数据保持一致 |
| 401 双重处理 | 后端 401 可能既走 Result.code=401 又走真实 HTTP 401 | `utils/request.ts` 写独立 `handleUnauthorized()`，两处都调用；保证不触发二次 refresh 死循环 |
| 明暗切换仅预留钩子 | 仅引入 dark/css-vars.css + isDark store + config-provider class | 不提前写死 `--el-color-primary`，让 UI/UX 智能体后续填充 |
| 下载中文文件名 | Content-Disposition: `filename*=utf-8''%E8%B4%A6...` | `utils/auth.ts` 提供 `parseFilenameFromDisposition(header)` 用 decodeURIComponent + RFC 5987 正则解析 |
| 修改密码接口缺失（跨端） | 顶栏菜单已承诺该功能，但后端无 `PUT /api/user/password`，无法联调 | **后端待办**：HLD/详细设计补接口（校验旧密码 1006、成功自增 token_version），前端 `ModifyPasswordDialog` 与之联调；改密成功会使当前会话登出 |
| userInfo 契约（跨端） | 后端 user 表无 email 列，前端旧契约 `userInfo.email/userVersion` 不存在 | **后端待办**：/api/user/info 返回 `{ id, username, nickname }`；前端 types 已按此对齐，联调前须后端确认 |
| 导出契约（跨端） | 后端 export_task 无 `processedRows`，字段为 `row_count/file_size/error_msg`；状态 3=失败、4=过期 | **后端待办**：ExportTaskVO 按 `{ taskId, status, rowCount, fileSize, fileName, errorMsg, createTime }` 返回；前端轮询 `status===2` 才下载 |

### 12.7 开发环境路由与跳转闭环（grill-me 共识）

> 生产环境由 Nginx 处理（§12.6）；开发环境由 Vite dev server 中间件模拟相同行为，确保 dev/prod 体验一致。

#### 12.7.1 问题背景
开发环境直接访问 `localhost:5173/` 时，Vite 默认返回 `index.html`（Vue 入口）→ Vue 路由 `/` 重定向 `/dashboard` → 路由守卫发现无 token → 跳 `/login`。用户"启动即见介绍页"的诉求无法满足。

#### 12.7.2 Vite 中间件方案（landingMiddleware）
在 `vite.config.ts` 内联自定义插件 `landingMiddleware()`，注册为 dev server 中间件：

| 拦截路径 | 行为 |
|---|---|
| `GET /`（无 `refresh_token` cookie） | 返回 `public/landing/index.html`（介绍页） |
| `GET /`（有 `refresh_token` cookie） | 302 跳 `/app/dashboard`（已登录直达工作台） |

### 13.9 SSE 流式处理（utils/sse.ts）

```typescript
// SSE 帧解析：data: {"type":"chunk","content":"已"}
interface AiStreamFrame {
  type: 'chunk' | 'tool_call' | 'done' | 'error';
  content?: string;
  tool?: string;
  result?: any;
  errorCode?: number;
  errorMessage?: string;
}

// 使用 fetch + ReadableStream 而非 EventSource（支持 POST + Authorization 头）
async function streamAiChat(
  message: string,
  sessionId: string | null,
  onChunk: (frame: AiStreamFrame) => void,
  onError: (err: Error) => void,
  onDone: () => void
): Promise<AbortController> {
  const controller = new AbortController();
  const resp = await fetch('/api/ai/chat', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${useUserStore().accessToken}`,
    },
    credentials: 'include',
    body: JSON.stringify({ message, sessionId }),
    signal: controller.signal,
  });

  const reader = resp.body!.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop() || '';
    for (const line of lines) {
      if (line.startsWith('data: ')) {
        const frame: AiStreamFrame = JSON.parse(line.slice(6));
        onChunk(frame);
        if (frame.type === 'done') onDone();
        if (frame.type === 'error') onError(new Error(frame.errorMessage));
      }
    }
  }
  return controller;
}
```

> **为何不用 `EventSource`**：`EventSource` 仅支持 GET 请求且无法自定义 Authorization 头，而 AI 对话需 POST + Bearer Token，故使用 `fetch + ReadableStream` 手动解析 SSE 帧。

  },

### 13.15 被舍弃的方案

| 方案 | 舍弃理由 |
|---|---|
| 独立 AI 对话页作为唯一入口 | 切换上下文成本高，悬浮抽屉更易用 |
| WebSocket 双向通信 | SSE 单向推送已满足需求，实现更简单，Nginx 配置更简洁 |
| AI 消息纯文本渲染 | Markdown 渲染支持表格/列表/代码块，AI 输出更丰富 |
| 每次对话都新建会话 | 会话列表管理历史，用户可续接上下文 |
| AI 直接修改预算（无需确认） | 写操作要求二次确认，避免 AI 误操作 |
