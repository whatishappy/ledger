## 1. 引言

### 1.1 项目背景

在个人财务管理领域，传统记账方式（纸质账本、Excel表格）存在**操作繁琐、数据孤立、缺乏智能化分析**三大痛点。用户难以从零散的消费记录中获得有价值的财务洞察，更无法有效进行预算规划与风险预警。

### 1.2 立项目的与项目目标

本项目旨在构建一款**轻量级、高可用、可扩展**的个人云端记账系统。它以“**极简操作 + 数据驱动 + 智能演进**”为核心理念。

**核心价值主张：**

- **对用户**：提供3秒极速记账体验、多维度财务仪表盘、主动式预算预警、AI 智能记账与财务洞察
- **对团队**：沉淀可复用的技术组件与开发规范
- **对技术演进**：AI 驱动的个人记账（自然语言记账、小票 OCR、智能预算、财务周报等）

**项目目标（SMART原则）：**

| 目标维度     | 具体指标                                                     |
| :----------- | :----------------------------------------------------------- |
| **业务目标** | 注册→记账→统计→预算→导出全流程闭环，核心操作路径≤3步         |
| **性能目标** | 仪表盘接口响应时间≤200ms（缓存命中率≥90%），单实例支撑100+ QPS |
| **质量目标** | 核心接口测试覆盖率≥80%，线上故障率≤1次/月                    |
| **交付目标** | **11.5个工作日**内完成开发、测试与Docker部署上线（含1天缓冲） |
| **扩展目标** | AI 能力以 Tool 形式接入现有 Service，新增 AI 场景时无需重构核心业务代码 |

## 4. 数据库设计

```
CREATE TABLE `user` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT,
  `username` varchar(50) NOT NULL COMMENT '登录名',
  `password` varchar(255) NOT NULL COMMENT 'BCrypt加密',
  `nickname` varchar(50) DEFAULT NULL,

  `created_at` datetime DEFAULT CURRENT_TIMESTAMP,
  `updated_at` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

- **`transaction_image.file_url`**：MinIO 对象路径，与 `export_task.file_url` 复用同一对象存储。
- **`scheduled_transaction.cron_expression`**：Quartz 风格 Cron（如 `0 0 0 1 * ?` 每月1日），`next_execute_time` 由调度器滚动计算。
- **`ai_chat_message.role`**：取值 `user` / `assistant` / `tool`，对齐 LangChain4j 消息模型。
- **`ai_chat_message.extra_json`**：JSON 字段，记录 Tool 调用信息、Token 用量、模型名称等。
- **`ai_report_task.status`**：0-待处理 / 1-处理中 / 2-已完成 / 3-失败，失败时按 10s/30s/90s 退避重试 3 次。
- **`ai_knowledge_document.milvus_id`**：对应 Milvus 集合 `ledger_knowledge` 中的向量 ID。

> AI 相关表（6~9）的字段定义与存储架构详见 [AI 模块需求分析](file:///f:/ledger/docs/个人记账本——AI模块需求分析.md) 第 6 章。

## 5. 缓存策略设计

### 5.1 缓存Key设计

| 缓存场景      | 缓存Key                      | 过期时间 | 失效策略                    |
| :------------ | :--------------------------- | :------- | :-------------------------- |
| 月度仪表盘    | `dashboard:{userId}:{month}` | 5分钟    | 账目/预算变更时**精确删除** |
| 预算列表      | `budget:{userId}:{month}`    | 10分钟   | 预算变更时**精确删除**      |
| 用户信息      | `user:{userId}`              | 30分钟   | 用户信息更新时删除          |
| 用户Token版本 | `token:version:{userId}`     | 7天      | 改密时自增                  |
| 记账幂等      | `idempotent:account:{key}`   | 5分钟    | 自动过期                    |
| **用户标签列表（V2.0新增）** | `tags:{userId}` | 30分钟   | 标签增删改时删除            |
| **用户交易模板列表（V2.0新增）** | `templates:{userId}` | 30分钟 | 模板增删改时删除            |
| **AI 对话历史热数据（V2.0新增）** | `ai:chat:{userId}:{sessionId}` | 1小时 | 新消息时更新（Redis List 存最近100条） |
| **AI 每日配额（V2.0新增）** | `ai:quota:{userId}:{date}` | 24小时（至当日 23:59） | 每次对话累加（对话数+Token 数） |

### 5.2 跨月缓存双清（关键设计）

用户将账目日期从8月修改到9月时，**新旧两个月份**的dashboard和budget缓存均需清除。

### 5.3 事务与缓存一致性（关键设计）

> **⚠️ 风险修复**：缓存删除操作必须在**事务提交后**执行，避免事务回滚但缓存已删导致的数据不一致。

**执行顺序**：

1. 开启事务
2. 执行数据库更新
3. 提交事务（`@Transactional` 正常返回）
4. **事务提交后**执行缓存删除（使用 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`）

### 5.4 缓存删除兜底策略

| 策略           | 说明                                                    |
| :------------- | :------------------------------------------------------ |
| **短过期时间** | 即使删除失败，dashboard 5分钟、budget 10分钟后自动失效  |
| **异步重试**   | 监听缓存删除失败事件，异步重试3次（指数退避：1s/2s/4s） |
| **降级容忍**   | 缓存清除失败仅记录日志和指标，主业务不受影响            |

### 6.2 记账幂等设计（V1.5增强）

> **⚠️ 安全增强**：幂等Key由**服务端基于业务参数生成**，防止前端篡改导致幂等绕过。

**流程**：

text

```
1. 前端传入idempotentKey（可选，由服务端优先使用业务参数生成）
2. 服务端使用 userId + category + amount + accountDate 计算MD5作为幂等Key
3. 检查Redis是否已有该Key → 有则返回原账目ID
4. 无则执行记账，写入Redis（5分钟过期）
```



### 6.3 参数校验边界

| 字段           | 校验规则                           | 错误码 |
| :------------- | :--------------------------------- | :----- |
| `amount`       | > 0，最多两位小数                  | 400    |
| `type`         | 0 或 1                             | 400    |
| `category`     | 预定义枚举值                       | 400    |
| `month`        | 格式 `\d{4}-\d{2}`，不能晚于当前月 | 400    |
| `account_date` | 不能晚于当前日期+7天               | 400    |

## 7. 非功能性需求

### 7.1 安全设计（V1.5增强：用户版本号方案）

> **优化说明**：V1.4中使用黑名单存储全量Token，内存消耗随在线设备数增长。V1.5改为**用户版本号**方案，仅存储一个整数，节省Redis内存。

| 机制                        | 实现方式                                                     | 内存占用 |
| :-------------------------- | :----------------------------------------------------------- | :------- |
| **Token失效（用户版本号）** | 用户表 `token_version` 字段，登录时写入JWT Claims，改密/注销时自增 | O(1)     |
| **Access Token**            | 有效期2小时，包含 `tokenVersion` 声明                        | —        |
| **Refresh Token**           | 有效期7天，包含 `tokenVersion` 声明                          | —        |
| **登出**                    | 客户端丢弃Token，服务端无状态                                | —        |

**校验逻辑**：

text

```
请求 → 解析Token → 验证签名&有效期 → 提取userId和tokenVersion
→ 查询用户表最新token_version → 比对 → 一致则放行，不一致则拒绝
```



| 类别            | 要求                                    |
| :-------------- | :-------------------------------------- |
| **密码安全**    | BCrypt加密存储（强度系数10）            |
| **数据传输**    | 生产环境强制HTTPS                       |
| **SQL注入防护** | MyBatis-Plus参数绑定（`#{}`）           |
| **接口限流**    | 导出：5分钟/次/用户；登录：10次/分钟/IP |

### 7.2 可靠性

| 类别            | 要求                              |
| :-------------- | :-------------------------------- |
| **数据库备份**  | 每日凌晨2:00全量备份，保留7天     |
| **数据恢复RTO** | ≤ 2小时                           |
| **数据恢复RPO** | ≤ 24小时                          |
| **缓存降级**    | Redis不可用时自动降级为直查数据库 |

## 9. 风险分析

| 风险项                | 影响 | 概率 | 缓解措施                                            |
| :-------------------- | :--- | :--- | :-------------------------------------------------- |
| **跨月缓存未双清**    | 高   | 中   | 设计文档强制约束，代码Review重点检查                |
| **事务与缓存一致性**  | 高   | 中   | 事务提交后删除缓存（`@TransactionalEventListener`） |
| **ThreadLocal泄露**   | 高   | 中   | Filter finally强制清理；压测验证                    |
| **导出任务丢失**      | 中   | 中   | 任务状态持久化DB；启动时恢复机制                    |
| **EasyExcel内存溢出** | 高   | 中   | 同步导出限制10000行；超限走异步导出                 |
