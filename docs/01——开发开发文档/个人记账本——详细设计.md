## 3. 安全模块详细设计

### 3.1 模块职责

安全模块负责系统的身份认证与授权管理，核心职责包括：
- JWT Token的解析、签名校验、有效期校验
- 用户Token版本号校验（改密/注销时所有旧Token失效）
- Refresh Token换取新Access Token
- 登录态管理（登出、Token失效处理）
- 用户上下文信息在线程中的传递与清理

### 3.2 核心类/方法签名定义

| 类名                    | 方法签名                                            | 入参                                                 | 出参    | 职责                      |
| :---------------------- | :-------------------------------------------------- | :--------------------------------------------------- | :------ | :------------------------ |
| JwtUtils                | generateAccessToken(userId, username, tokenVersion) | userId:Long, username:String, tokenVersion:Integer   | String  | 生成Access Token          |
| JwtUtils                | generateRefreshToken(userId, tokenVersion)          | userId:Long, tokenVersion:Integer                    | String  | 生成Refresh Token         |
| JwtUtils                | parseToken(token)                                   | token:String                                         | Claims  | 解析Token，提取声明信息   |
| JwtUtils                | validateToken(token)                                | token:String                                         | Boolean | 验证Token签名与有效期     |
| JwtUtils                | extractUserId(token)                                | token:String                                         | Long    | 从Token提取用户ID         |
| JwtUtils                | extractTokenVersion(token)                          | token:String                                         | Integer | 从Token提取版本号         |
| JwtAuthenticationFilter | doFilterInternal(request, response, chain)          | HttpServletRequest, HttpServletResponse, FilterChain | void    | Token校验，设置用户上下文 |
| TokenVersionService     | getTokenVersion(userId)                             | userId:Long                                          | Integer | 获取用户最新Token版本号   |
| TokenVersionService     | incrementTokenVersion(userId)                       | userId:Long                                          | void    | 用户Token版本号自增       |

### 3.3 JWT Token双机制设计

**Access Token**：
- 有效期：2小时
- 存储位置：客户端内存
- 传递方式：请求头 Authorization: Bearer {token}
- Claims内容：userId（主体）、username、tokenVersion（关键）、签发时间、过期时间

**Refresh Token**：
- 有效期：7天
- 存储位置：HttpOnly Cookie（防止XSS攻击）
- 传递方式：Cookie自动携带
- 用途：Access Token过期时，客户端调用刷新接口换取新Access Token

### 3.4 用户Token版本号机制

**设计目的**：替代黑名单方案，解决改密/注销时旧Token失效问题，节省Redis内存。

**核心逻辑**：
- 用户表增加 token_version 字段，默认值为1。
- 登录时，将当前 token_version 写入JWT的Claims中。
- 每次请求到达时，拦截器解析Token后，从数据库/缓存查询用户最新的 token_version。
- 比对Token中的版本号与当前版本号：
  - 一致 → 放行
  - 不一致 → 拒绝，提示重新登录
- 用户修改密码或注销账号时，执行 `token_version = token_version + 1`。

### 3.5 Token刷新流程

1. 客户端发现Access Token过期（API返回401）。
2. 客户端携带Refresh Token（自动从Cookie读取）调用 `/api/auth/refresh`。
3. 服务端验证Refresh Token签名和有效期。
4. 服务端从Refresh Token提取userId，查询用户最新 token_version。
5. 验证Refresh Token中的版本号与当前版本号一致。
6. 生成新的Access Token返回给客户端。
7. 若Refresh Token已过期或版本号不一致，返回错误，强制用户重新登录。

### 3.6 线程上下文管理

**设计要点**：
- 使用ThreadLocal存储当前请求的用户ID。
- 在JWT认证过滤器中，解析成功后调用 `UserContext.setUserId(userId)`。
- 在过滤器的 `finally` 块中调用 `UserContext.clear()` 强制清理。
- 业务层通过 `UserContext.getUserId()` 获取当前用户ID。

**约束**：禁止在业务层手动清理ThreadLocal；禁止在异步线程中直接传递ThreadLocal。


## 4. 用户模块详细设计

### 4.1 模块职责

用户模块负责系统用户的生命周期管理，核心职责包括：
- 用户注册（用户名唯一性校验、密码加密）
- 用户登录（身份验证、Token签发）
- 当前用户信息查询
- 用户登出（客户端Token清除，服务端无状态）
- 账号注销（数据脱敏、Token失效）

### 4.2 功能点清单

| :------- | :----------- | :----- | :------------------------------------------ |
| U-01     | 用户注册     | P0     | 用户名+密码注册，密码BCrypt加密，用户名唯一 |
| U-02     | 用户登录     | P0     | 验证凭证，返回Access Token和Refresh Token   |
| U-03     | 获取用户信息 | P1     | 返回当前登录用户基本信息                    |
| U-04     | 用户登出     | P1     | 客户端清除Token，服务端无状态（版本号方案） |
| U-05     | Token刷新    | P0     | 用Refresh Token换取新Access Token           |
| U-06     | 账号注销     | P1     | 数据脱敏、Token失效、财务数据保留           |
| U-07     | 修改密码     | P1     | 校验旧密码，成功后自增Token版本号使旧Token失效 |

### 4.3 功能U-01：用户注册

| 项目           | 内容                                                         |
| :------------- | :----------------------------------------------------------- |
| **功能描述**   | 新用户通过用户名和密码创建账户，密码经BCrypt加密存储。       |
| **输入参数**   | username（字符串，3-50位，字母/数字/下划线）、password（字符串，6-100位） |
| **输出结果**   | 注册成功/失败信息                                            |
| **业务规则**   | ① 用户名全局唯一，重复时返回错误码1001。<br>② 密码使用BCrypt加密（强度系数10），不存储明文。<br>③ 昵称默认取用户名。<br>④ 用户状态默认为正常（status=1）。<br>⑤ token_version默认为1。 |
| **处理流程**   | 步骤1：校验用户名格式和密码格式。<br>步骤2：查询数据库确认用户名是否已存在。<br>步骤3：若存在，终止流程，返回错误码1001。<br>步骤4：若不存在，对密码进行BCrypt加密。<br>步骤5：构建用户实体，设置用户名、加密密码、昵称、默认状态、默认版本号。<br>步骤6：调用数据层保存用户记录。<br>步骤7：返回注册成功。 |
| **异常场景**   | ① 用户名已存在 → 错误码1001。<br>② 用户名格式不合法 → 错误码400。<br>③ 密码长度不合规 → 错误码400。 |
| **涉及数据表** | user（username, password, nickname, status, token_version, created_at, updated_at） |

### 4.4 功能U-02：用户登录

| 项目           | 内容                                                         |
| :------------- | :----------------------------------------------------------- |
| **功能描述**   | 验证用户凭证，登录成功后返回Access Token和Refresh Token。    |
| **输入参数**   | username（字符串）、password（字符串）                       |
| **输出结果**   | Access Token（String）、Refresh Token（写入Cookie）、用户信息 UserVO（id/username/nickname） |
| **业务规则**   | ① 登录失败统一返回1002，不区分“用户不存在”和“密码错误”（防撞库）。<br>② 登录成功后，从数据库读取当前token_version写入Token。<br>③ Refresh Token写入HttpOnly Cookie，客户端无法通过JS读取（防XSS）。 |
| **处理流程**   | 步骤1：校验用户名和密码不为空。<br>步骤2：根据用户名查询用户记录。<br>步骤3：若用户不存在，返回错误码1002。<br>步骤4：若用户存在，使用BCrypt比对明文密码与密文密码。<br>步骤5：若密码不匹配，返回错误码1002。<br>步骤6：若密码匹配，读取用户token_version。<br>步骤7：生成Access Token（有效期2小时）。<br>步骤8：生成Refresh Token（有效期7天）。<br>步骤9：将Refresh Token写入HttpOnly Cookie。<br>步骤10：返回Access Token给客户端。 |
| **异常场景**   | ① 用户不存在或密码错误 → 错误码1002。<br>② 用户状态为已注销（status=0）→ 错误码1002。 |
| **涉及数据表** | user（username, password, token_version, status）            |

### 4.5 功能U-06：账号注销

| 项目             | 内容                                                         |
| :--------------- | :----------------------------------------------------------- |
| **功能描述**     | 用户注销账号，触发数据脱敏和Token失效，历史财务数据保留。    |
| **输入参数**     | password（字符串，当前密码验证）                             |
| **输出结果**     | 注销成功/失败信息                                            |
| **业务规则**     | ① 必须验证当前密码，防止恶意注销。<br>② 用户名脱敏为 `user_del_{时间戳}`。<br>③ 昵称改为“已注销用户”。<br>④ 用户状态置为0（已注销）。<br>⑤ token_version自增1，使所有旧Token失效。<br>⑥ account_book和budget数据完整保留（不删除）。<br>⑦ 清除该用户所有Redis缓存。<br>⑧ 异步清理该用户的导出文件。 |
| **处理流程**     | 步骤1：从线程上下文获取当前用户ID。<br>步骤2：查询用户当前密码密文和状态。<br>步骤3：校验传入密码与密文是否匹配。<br>步骤4：不匹配则终止，返回错误码1006。<br>步骤5：匹配则更新用户记录：用户名脱敏、昵称变更、状态置为已注销、token_version自增。<br>步骤6：清除该用户所有缓存Key。<br>步骤7：异步提交导出文件清理任务。<br>步骤8：返回注销成功。 |
| **异常场景**     | ① 密码错误 → 错误码1006。<br>② 用户不存在 → 错误码1003。<br>③ 用户已注销 → 错误码1003。 |
| **涉及数据表**   | user（username, nickname, status, token_version, updated_at） |
| **数据合规说明** | 财务数据保留7年（满足会计档案管理要求），用户信息脱敏后保留（满足审计追溯） |

### 4.6 功能U-07：修改密码

| 项目           | 内容                                                         |
| :------------- | :----------------------------------------------------------- |
| **功能描述**   | 用户修改登录密码，成功后所有旧Token失效，强制重新登录。      |
| **输入参数**   | oldPassword（字符串，当前密码验证）、newPassword（字符串，6-100位） |
| **输出结果**   | 修改成功/失败信息                                            |
| **业务规则**   | ① 必须校验旧密码，防止越权改密。<br>② 新密码长度6-100位，复用注册规则。<br>③ 成功后 `token_version` 自增1，所有旧Access/Refresh Token立即失效（含当前会话）。<br>④ 改密成功即视为强制登出，前端需清空会话并跳转登录页。 |

| **异常场景**   | ① 旧密码错误 → 错误码1006。<br>② 新密码格式不合法 → 错误码400。<br>③ 用户不存在/已注销 → 错误码1003。 |
| **涉及数据表** | user（password, token_version, updated_at） |


## 5. 账目模块详细设计

### 5.1 模块职责

账目模块是系统的核心业务模块，负责用户收支记录的全生命周期管理，核心职责包括：
- 新增记账（含幂等设计，防止重复提交）
- 修改记账（含跨月缓存双清）
- 删除记账（逻辑删除，数据可恢复）
- 分页条件查询（支持多维度筛选）

### 5.2 功能点清单

| 功能编号 | 功能名称     | 优先级 | 简要说明                                  |
| :------- | :----------- | :----- | :---------------------------------------- |
| A-01     | 新增记账     | P0     | 记录收支，含幂等设计，Key由服务端生成     |
| A-02     | 分页条件查询 | P0     | 按时间倒序，支持类型/分类/日期/关键词筛选 |
| A-03     | 修改记账     | P0     | 含跨月缓存双清、乐观锁防止并发覆盖        |
| A-04     | 删除记账     | P0     | 逻辑删除（is_deleted=1），数据可恢复      |

### 5.3 功能A-01：新增记账

| 项目           | 内容                                                         |
| :------------- | :----------------------------------------------------------- |
| **功能描述**   | 记录一笔收支明细，包含收支类型、分类、金额、业务日期、备注。支持幂等，防止重复提交。 |
| **输入参数**   | type（0-支出/1-收入）、category（枚举值）、amount（>0，最多两位小数）、accountDate（业务日期）、remark（可选）、extraJson（可选） |
| **输出结果**   | 新生成的账目ID                                               |
| **业务规则**   | ① 金额必须大于0，否则拒绝。<br>② 分类必须为预定义枚举值。<br>③ 业务日期不能晚于当前日期+7天。<br>④ user_id由后端从线程上下文自动注入，前端不传递。<br>⑤ 同一用户相同分类+金额+日期的请求在5分钟内视为重复，返回已有ID。<br>⑥ 幂等Key由服务端基于业务字段生成，不信任前端传入。<br>⑦ 新增成功后，发布账目变更事件（用于事务提交后清除缓存）。 |
| **处理流程**   | 步骤1：从线程上下文获取当前用户ID。<br>步骤2：校验金额、分类、业务日期合法性。<br>步骤3：基于用户ID+分类+金额+业务日期生成幂等Key。<br>步骤4：查询Redis中是否已存在该幂等Key。<br>步骤5：若存在，直接返回已有的账目ID，流程结束。<br>步骤6：若不存在，构建账目实体，设置用户ID及所有字段。<br>步骤7：调用数据层保存账目记录。<br>步骤8：以幂等Key为键，账目ID为值存入Redis，过期时间5分钟。<br>步骤9：发布账目变更事件（含用户ID和新账目的月份）。<br>步骤10：返回新生成的账目ID。 |
| **异常场景**   | ① 金额≤0 → 错误码400。<br>② 分类不在枚举范围 → 错误码400。<br>③ 业务日期超出允许范围 → 错误码400。<br>④ 数据库异常 → 错误码500。 |
| **涉及数据表** | account_book（user_id, type, category, amount, account_date, remark, extra_json, version, is_deleted, create_time, update_time） |
| **性能约束**   | 接口响应时间P95 ≤ 100ms（不含网络延迟）；幂等Key查询为Redis操作，延迟<1ms |

### 5.5 功能A-03：修改记账

| **异常场景**   | ① 账目不存在或不属于当前用户 → 错误码2001。<br>② 乐观锁冲突 → 错误码2002。<br>③ 金额/分类/日期校验失败 → 错误码400。 |
| **涉及数据表** | account_book（全字段更新，version作为乐观锁条件）            |
| **性能约束**   | 缓存删除在事务提交后异步执行，不影响主流程响应时间           |

### 6.3 功能B-01：设定月度预算

| 项目           | 内容                                                         |

| **功能描述**   | 为指定支出分类设定月度预算上限。同一用户同一分类同一月份仅可存在一条预算。 |
| **输入参数**   | category（枚举值）、month（YYYY-MM）、amountLimit（>0）      |
| **输出结果**   | 新生成的预算ID                                               |
| **业务规则**   | ① 仅支出类分类可设定预算（收入类不允许）。<br>② 同一用户同一分类同一月份只能有一条预算（数据库唯一索引兜底）。<br>③ 预算金额必须大于0。<br>④ 月份不能晚于当前月份。 |
| **处理流程**   | 步骤1：从线程上下文获取当前用户ID。<br>步骤2：校验分类、月份、金额合法性。<br>步骤3：查询是否存在相同用户+分类+月份的预算记录。<br>步骤4：若存在，终止流程，返回错误码3001。<br>步骤5：若不存在，构建预算实体。<br>步骤6：调用数据层保存预算记录。<br>步骤7：发布预算变更事件（清除对应月份缓存）。<br>步骤8：返回新生成的预算ID。 |

| **涉及数据表** | budget（user_id, category, month, amount_limit, version, is_deleted, create_time, update_time） |

### 6.4 功能B-04：查询预算列表

| 项目           | 内容                                                         |
| :------------- | :----------------------------------------------------------- |
| **功能描述**   | 查询指定月份的所有预算设定，并实时计算每个分类的已消费金额和进度百分比。 |
| **输入参数**   | month（格式YYYY-MM）                                         |
| **输出结果**   | 预算列表，每条包含：category、amountLimit、spent、progress（%）、isOverBudget |
| **业务规则**   | ① 预算进度 = 已消费金额 / 预算上限 × 100%。<br>② 已消费金额 = 该月该分类所有支出账目金额之和。<br>③ 进度超过100%时标记为超支（isOverBudget=true）。<br>④ 仅展示支出分类的预算（收入类不涉及预算）。 |
| **处理流程**   | 步骤1：从线程上下文获取当前用户ID。<br>步骤2：校验月份格式（YYYY-MM），且不晚于当前月份。<br>步骤3：查询该用户该月的所有预算记录。<br>步骤4：若无预算，返回空列表。<br>步骤5：计算该月月初和月末日期。<br>步骤6：一次性查询该月所有支出分类的汇总金额（GROUP BY category）。<br>步骤7：将查询结果转为Map（分类 → 已消费总额）。<br>步骤8：遍历预算列表，从Map中获取每个分类的已消费金额（无记录则为0）。<br>步骤9：逐个计算进度百分比和超支状态。<br>步骤10：组装并返回预算进度列表。 |
| **关键优化**   | ① 禁止在循环中逐条查询account_book（原方案存在N+1问题）。<br>② 使用GROUP BY一次性获取所有分类汇总，SQL执行次数固定为2次。<br>③ 使用缓存（过期时间10分钟），减少数据库查询频率。 |
| **涉及数据表** | budget（预算定义）+ account_book（实际消费汇总）             |
| **性能约束**   | SQL执行次数 ≤ 2次；缓存命中时响应时间 ≤ 10ms；缓存失效时响应时间 ≤ 200ms |

| 项目           | 内容                                                         |

| **涉及数据表** | account_book（收入/支出汇总、分类占比、趋势）                |

### 10.2 表结构详细设计

#### 10.2.1 用户表（user）

**表说明**：存储系统用户账户信息，包含身份认证、密码管理、Token版本控制等核心字段。

| 字段名        | 类型         | 约束                        | 说明                         | 业务用途                                                     |
| :------------ | :----------- | :-------------------------- | :--------------------------- | :----------------------------------------------------------- |
| id            | BIGINT(20)   | PK, AUTO_INCREMENT          | 用户ID                       | 全局唯一标识，所有业务表的外键关联目标                       |
| username      | VARCHAR(50)  | UNIQUE, NOT NULL            | 登录用户名                   | 用户登录凭证，唯一性校验保障账户不重复                       |
| password      | VARCHAR(255) | NOT NULL                    | BCrypt加密密码               | 存储用户密码密文，即使数据库泄露也无法还原明文               |
| nickname      | VARCHAR(50)  | —                           | 用户昵称                     | 前端展示用，注册时默认取username                             |
| avatar_url    | VARCHAR(500) | —                           | 头像URL（V2.0新增）          | 存 MinIO 对象路径，前端展示用户头像；空时使用默认头像         |
| token_version | INT(11)      | DEFAULT 1                   | Token版本号                  | **核心安全字段**。改密/注销时自增，使所有旧Token失效（替代黑名单方案） |
| status        | TINYINT(1)   | DEFAULT 1                   | 账户状态（1-正常，0-已注销） | 控制账户是否可用，注销后不可登录                             |
| created_at    | DATETIME     | DEFAULT CURRENT_TIMESTAMP   | 记录创建时间                 | 审计追踪，记录账户注册时间                                   |
| updated_at    | DATETIME     | ON UPDATE CURRENT_TIMESTAMP | 记录更新时间                 | 审计追踪，记录最后一次信息变更时间                           |

**索引策略**：

| 索引名      | 字段     | 类型     | 用途                                       |
| :---------- | :------- | :------- | :----------------------------------------- |
| PRIMARY     | id       | 主键     | 按ID快速查询                               |
| uk_username | username | 唯一索引 | 注册时用户名唯一性校验，登录时按用户名查询 |

**DDL语句**：

```sql
CREATE TABLE `user` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  `username` varchar(50) NOT NULL COMMENT '登录用户名',
  `password` varchar(255) NOT NULL COMMENT 'BCrypt加密密码',
  `nickname` varchar(50) DEFAULT NULL COMMENT '用户昵称',
  `avatar_url` varchar(500) DEFAULT NULL COMMENT '头像URL（V2.0新增，存MinIO对象路径）',
  `token_version` int(11) DEFAULT '1' COMMENT 'Token版本号（改密/注销时自增，旧Token失效）',
  `status` tinyint(1) DEFAULT '1' COMMENT '账户状态：1-正常，0-已注销',
  `created_at` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户账户表';
```

**字段设计决策说明**：

| 设计决策          | 理由                                                   |
| :---------------- | :----------------------------------------------------- |
| 用户名唯一索引    | 保障注册时用户名不重复，同时加速登录查询               |
| BCrypt加密        | 不可逆哈希算法，含随机盐值，有效防御彩虹表和暴力破解   |
| token_version字段 | 替代黑名单方案，仅存储一个整数，内存消耗从O(n)降到O(1) |
| status字段        | 支持账号软注销，用户数据保留但不可用，满足审计追溯需求 |


#### 10.2.2 账目表（account_book）

**表说明**：存储用户每一笔收支明细，是系统的核心业务表。所有统计分析、预算进度计算均基于此表。

| 字段名       | 类型          | 约束                        | 说明                                      | 业务用途                                              |
| :----------- | :------------ | :-------------------------- | :---------------------------------------- | :---------------------------------------------------- |
| id           | BIGINT(20)    | PK, AUTO_INCREMENT          | 账目ID                                    | 全局唯一标识，修改/删除时用于定位                     |
| user_id      | BIGINT(20)    | NOT NULL                    | 所属用户ID                                | **数据隔离关键字段**，所有查询强制带此条件            |
| type         | TINYINT(1)    | NOT NULL                    | 收支类型（1-收入，0-支出）                | 区分资金流向，计算结余时使用                          |
| category     | VARCHAR(20)   | NOT NULL                    | 收支分类（餐饮/交通/购物/工资/娱乐/其他） | 统计分析的核心维度，分类占比和预算按此字段分组        |
| amount       | DECIMAL(10,2) | NOT NULL                    | 金额（精确到分）                          | 核心数值字段，所有汇总计算基于此字段                  |
| account_date | DATE          | NOT NULL                    | 业务发生日期（支持补录）                  | 统计分析的**时间维度**，所有月度/趋势统计按此日期分组 |
| remark       | VARCHAR(255)  | —                           | 备注描述                                  | 用户可读的补充信息，支持模糊搜索                      |
| extra_json   | JSON          | —                           | 扩展JSON字段                              | 存储AI标签、图片ID等未来扩展数据，无需改表结构        |
| version      | INT(11)       | DEFAULT 1                   | 乐观锁版本号                              | **并发控制字段**，更新时校验防止覆盖                  |
| is_deleted   | TINYINT(1)    | DEFAULT 0                   | 逻辑删除标识（0-未删除，1-已删除）        | 支持数据软删除，查询自动过滤已删记录                  |
| create_time  | DATETIME      | DEFAULT CURRENT_TIMESTAMP   | 系统入库时间                              | 审计追踪，记录数据何时写入系统                        |
| update_time  | DATETIME      | ON UPDATE CURRENT_TIMESTAMP | 系统更新时间                              | 审计追踪，记录数据最后一次修改时间                    |

**索引策略**：

| 索引名            | 字段                  | 类型     | 用途                                                    |
| :---------------- | :-------------------- | :------- | :------------------------------------------------------ |
| PRIMARY           | id                    | 主键     | 按ID快速查询/修改/删除                                  |
| idx_user_date     | user_id, account_date | 复合索引 | **最核心查询**：按用户+业务日期范围的分页查询和统计汇总 |
| idx_user_category | user_id, category     | 复合索引 | 按用户+分类筛选查询，加速分类占比统计                   |

**DDL语句**：

```sql
CREATE TABLE `account_book` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '账目ID',
  `user_id` bigint(20) NOT NULL COMMENT '所属用户ID',
  `type` tinyint(1) NOT NULL COMMENT '收支类型：1-收入，0-支出',
  `category` varchar(20) NOT NULL COMMENT '收支分类：餐饮/交通/购物/工资/娱乐/其他',
  `amount` decimal(10,2) NOT NULL COMMENT '金额（精确到分）',
  `account_date` date NOT NULL COMMENT '业务发生日期（支持补录）',
  `remark` varchar(255) DEFAULT NULL COMMENT '备注描述',
  `extra_json` json DEFAULT NULL COMMENT '扩展JSON字段（AI标签等）',
  `version` int(11) DEFAULT '1' COMMENT '乐观锁版本号',
  `is_deleted` tinyint(1) DEFAULT '0' COMMENT '逻辑删除标识：0-未删除，1-已删除',
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '系统入库时间',
  `update_time` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '系统更新时间',
  PRIMARY KEY (`id`),
  KEY `idx_user_date` (`user_id`, `account_date`),
  KEY `idx_user_category` (`user_id`, `category`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='账目记录主表';
```

**字段设计决策说明**：

| 设计决策                        | 理由                                                         |
| :------------------------------ | :----------------------------------------------------------- |
| DECIMAL(10,2)                   | 金额使用精确十进制类型，避免浮点数精度丢失问题               |
| account_date与create_time分离   | 支持补录场景（8月17日补录8月15日的账单），统计以业务日期为准 |
| 复合索引(user_id, account_date) | 典型查询场景是“查看某用户某月的账目”，此索引可快速定位       |
| extra_json JSON类型             | 支持动态扩展字段（如AI标签），无需频繁执行ALTER TABLE        |
| version + @Version              | MyBatis-Plus乐观锁实现，防止并发更新覆盖                     |
| is_deleted + @TableLogic        | MyBatis-Plus逻辑删除实现，查询自动过滤已删数据               |


#### 10.2.3 预算表（budget）

**表说明**：存储用户为各支出分类设定的月度预算上限，支持预算进度追踪和超支预警。

| 字段名       | 类型          | 约束                        | 说明                | 业务用途                                      |
| :----------- | :------------ | :-------------------------- | :------------------ | :-------------------------------------------- |
| id           | BIGINT(20)    | PK, AUTO_INCREMENT          | 预算ID              | 全局唯一标识                                  |
| user_id      | BIGINT(20)    | NOT NULL                    | 所属用户ID          | 数据隔离关键字段                              |
| category     | VARCHAR(20)   | NOT NULL                    | 支出分类            | 关联account_book.category，仅支出类可设定预算 |
| month        | VARCHAR(7)    | NOT NULL                    | 预算月份（YYYY-MM） | 按月粒度管理预算                              |
| amount_limit | DECIMAL(10,2) | NOT NULL                    | 预算上限金额        | 与当月实际支出比对，计算进度百分比            |
| version      | INT(11)       | DEFAULT 1                   | 乐观锁版本号        | 并发更新控制                                  |
| is_deleted   | TINYINT(1)    | DEFAULT 0                   | 逻辑删除标识        | 支持预算历史数据保留                          |
| create_time  | DATETIME      | DEFAULT CURRENT_TIMESTAMP   | 创建时间            | 审计追踪                                      |
| update_time  | DATETIME      | ON UPDATE CURRENT_TIMESTAMP | 更新时间            | 审计追踪                                      |

**索引策略**：

| 索引名                 | 字段                     | 类型     | 用途                                                 |
| :--------------------- | :----------------------- | :------- | :--------------------------------------------------- |
| PRIMARY                | id                       | 主键     | 按ID快速查询                                         |
| uk_user_category_month | user_id, category, month | 唯一索引 | **业务唯一约束**：同一用户同一分类同月仅一条预算记录 |
| idx_user_month         | user_id, month           | 复合索引 | 按用户+月份查询预算列表                              |

**DDL语句**：

```sql
CREATE TABLE `budget` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '预算ID',
  `user_id` bigint(20) NOT NULL COMMENT '所属用户ID',
  `category` varchar(20) NOT NULL COMMENT '支出分类（关联account_book.category）',
  `month` varchar(7) NOT NULL COMMENT '预算月份，格式：YYYY-MM',
  `amount_limit` decimal(10,2) NOT NULL COMMENT '月度预算上限金额',
  `version` int(11) DEFAULT '1' COMMENT '乐观锁版本号',
  `is_deleted` tinyint(1) DEFAULT '0' COMMENT '逻辑删除标识：0-未删除，1-已删除',
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_category_month` (`user_id`, `category`, `month`) COMMENT '唯一约束：同用户同分类同月仅一条记录',
  KEY `idx_user_month` (`user_id`, `month`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='月度预算表';
```

**字段设计决策说明**：

| 设计决策                           | 理由                                                        |
| :--------------------------------- | :---------------------------------------------------------- |
| 唯一索引(user_id, category, month) | 业务上不允许同一用户为同一分类在同月设定多条预算            |
| month使用VARCHAR(7)                | 格式统一为YYYY-MM，便于查询和比较，比DATE类型更节省索引空间 |
| 仅支持支出类预算                   | 收入无需预算，前端下拉仅展示支出分类                        |


#### 10.2.4 导出任务表（export_task）

**表说明**：管理异步导出任务的持久化状态，服务重启后任务不丢失，支持任务恢复和防重复执行。

| 字段名      | 类型         | 约束                        | 说明                                                       | 业务用途                                   |
| :---------- | :----------- | :-------------------------- | :--------------------------------------------------------- | :----------------------------------------- |
| id          | BIGINT(20)   | PK, AUTO_INCREMENT          | 任务ID                                                     | 全局唯一标识                               |
| task_id     | VARCHAR(64)  | UNIQUE, NOT NULL            | 任务唯一标识                                               | 客户端轮询查询的凭证                       |
| user_id     | BIGINT(20)   | NOT NULL                    | 发起用户ID                                                 | 数据隔离，下载时校验归属                   |
| status      | TINYINT(1)   | DEFAULT 0                   | 任务状态（0-待处理，1-处理中，2-已完成，3-失败，4-已过期） | 驱动任务状态机流转                         |
| file_url    | VARCHAR(500) | —                           | 文件访问路径                                               | 完成时记录下载地址                         |
| file_size   | BIGINT(20)   | —                           | 文件大小（字节）                                           | 下载时展示给用户                           |
| row_count   | INT(11)      | —                           | 导出行数                                                   | 展示给用户，了解导出规模                   |
| error_msg   | VARCHAR(255) | —                           | 失败原因                                                   | 任务失败时记录，便于排查                   |
| expire_time | DATETIME     | —                           | 文件过期时间                                               | 默认创建时间+7天，过期清理                 |
| create_time | DATETIME     | DEFAULT CURRENT_TIMESTAMP   | 任务创建时间                                               | 审计追踪                                   |
| update_time | DATETIME     | ON UPDATE CURRENT_TIMESTAMP | 最后更新时间                                               | 识别长时间卡住的任务（如处理中超过30分钟） |

**索引策略**：

| 索引名          | 字段            | 类型     | 用途                                          |
| :-------------- | :-------------- | :------- | :-------------------------------------------- |
| PRIMARY         | id              | 主键     | 按ID快速查询                                  |
| uk_task_id      | task_id         | 唯一索引 | 客户端按task_id查询状态                       |
| idx_user_status | user_id, status | 复合索引 | 按用户+状态查询任务列表，启动时恢复卡住的任务 |

**DDL语句**：

```sql
CREATE TABLE `export_task` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '任务ID',
  `task_id` varchar(64) NOT NULL COMMENT '任务唯一标识（客户端查询凭证）',
  `user_id` bigint(20) NOT NULL COMMENT '发起用户ID',
  `status` tinyint(1) NOT NULL DEFAULT '0' COMMENT '任务状态：0-待处理，1-处理中，2-已完成，3-失败，4-已过期',
  `file_url` varchar(500) DEFAULT NULL COMMENT '文件下载地址（完成时填充）',
  `file_size` bigint(20) DEFAULT NULL COMMENT '文件大小（字节）',
  `row_count` int(11) DEFAULT NULL COMMENT '导出行数',
  `error_msg` varchar(255) DEFAULT NULL COMMENT '失败原因（任务失败时填充）',
  `expire_time` datetime DEFAULT NULL COMMENT '文件过期时间（默认创建时间+7天）',
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '任务创建时间',
  `update_time` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '最后更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_task_id` (`task_id`),
  KEY `idx_user_status` (`user_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='导出任务管理表';
```

**任务状态机**：

```
待处理(0)  →  处理中(1)  →  已完成(2)  →  已过期(4)
              ↓ (异常)
              失败(3)  →  已过期(4)（清理时）
```

**字段设计决策说明**：

| 设计决策                    | 理由                                           |
| :-------------------------- | :--------------------------------------------- |
| 任务状态持久化              | 服务重启后任务不丢失，解决内存任务丢失问题     |
| task_id唯一索引             | 保证客户端轮询的task_id唯一，防冲突            |
| status=1且update_time>30min | 启动时扫描此类任务，重置为待处理，实现故障恢复 |
| file_url独立存储            | 支持本地卷和OSS两种存储方式切换                |
| expire_time预留             | 方便定时清理任务，无需依赖创建时间计算         |

### 10.4 数据量预估与扩容规划

| 表名         | 预估日增量                      | 年增量   | 2年数据量 | 推荐分表策略                           |
| :----------- | :------------------------------ | :------- | :-------- | :------------------------------------- |
| user         | 10条                            | 3,650条  | ~7,300条  | 无需分表                               |
| account_book | 100条/用户 × 100用户 = 10,000条 | 365万条  | ~730万条  | 单表≥500万行时，按account_date月份分表 |
| budget       | 1条/用户/月 × 100用户 = 100条   | 3.65万条 | ~7.3万条  | 无需分表                               |
| export_task  | 10条/天                         | 3,650条  | ~7,300条  | 无需分表                               |

**分表触发条件**：
- 单表数据量超过500万行
- 分页查询响应时间超过500ms
- 统计汇总查询响应时间超过1s

**分表方案**（V2.0实施）：
- 按 `account_date` 月度分表：`account_book_202501`、`account_book_202502`...
- 使用 ShardingSphere-JDBC 实现，业务代码无感知
- 当前月份的数据写入当月表，跨月查询自动路由多表


### 10.5 数据归档与清理策略

| 数据类型       | 保留周期             | 清理方式            | 清理时机     |
| :------------- | :------------------- | :------------------ | :----------- |
| 账目数据       | 永久保留（审计需求） | 不清理              | —            |
| 预算数据       | 永久保留             | 不清理              | —            |
| 导出任务记录   | 7天                  | 物理删除 + 文件删除 | 每日凌晨3:00 |
| 用户已注销数据 | 7年（会计档案要求）  | 脱敏保留            | —            |

**导出任务清理SQL**（定时任务执行）：
- 标记过期任务：UPDATE export_task SET status = 4 WHERE expire_time < NOW()
- 删除过期记录（7天前）：DELETE FROM export_task WHERE create_time < DATE_SUB(NOW(), INTERVAL 7 DAY)

> **接口契约对齐（与前端联调，V1.5 补充）**：
> - **userInfo / UserVO** = `{ id, username, nickname, avatarUrl }`（V2.0 新增 `avatarUrl` 字段，对应 `user.avatar_url` 列）。`GET /api/user/info` 与登录/刷新响应中的 userInfo 均按此返回。**不含 email**（user 表无该列）、**不含 token_version**（后端内部字段，前端无需持有）。
> - **ExportTaskVO** = `{ taskId, status, rowCount, fileSize, fileName, errorMsg, createTime }`，对应表字段 `row_count / file_size / error_msg`，`fileName` 取自 `file_url` 文件名部分，**无 processedRows 字段**。

### 15.1 AI 小票 OCR 模块（AI-06 ~ AI-07）

**模块职责**：上传小票/发票图片到 MinIO，调用 Agnes 多模态模型进行 OCR 识别，返回结构化数据（商户、金额、日期、明细）。

### 15.2 AI 支出预测模块

**核心方法**：`LedgerAiTools.predictExpense(userId, month)`

**预测算法**（历史趋势外推）：
1. 获取过去6个月的历史支出数据
2. 计算月均支出 `avgExpense`
3. 计算环比增长率 `trendRate = (近3月均值 - 前3月均值) / 前3月均值`
4. 预测值 = `avgExpense * (1 + trendRate)`
5. 返回：预测金额、置信度、上月实际、历史趋势数据

### 15.3 AI 预算智能推荐

**核心方法**：`LedgerAiTools.recommendBudget(userId, month)`

**推荐算法**：
1. 获取用户过去3个月各分类的支出数据
2. 对每个分类计算：历史均值、趋势系数
3. 推荐预算 = `历史均值 * (1 + 趋势系数)`，下限 = `历史均值 * 0.8`
4. 返回：当前预算、推荐预算、最低建议、建议信息

### 15.4 AI 财务周报

**核心方法**：`LedgerAiTools.generateWeeklyReport(userId)`

**周报内容**：
- 本周收支汇总（总收入、总支出、结余）
- 日均支出对比（本周 vs 上周）
- 分类支出排行TOP3
- 预算执行进度
- AI 建议（基于数据自动生成）

**定时任务**：`WeeklyReportScheduler` 每周一 09:00 自动执行（cron: `0 0 9 ? * MON`）

### 15.5 AI 省钱建议增强

**核心类**：`AiGuardService`

**切换机制**：

| 机制 | 触发条件 | 行为 |
| :--- | :--- | :--- |

| 自动恢复 | 降级状态下每2分钟探测 | 清除降级标记，进入恢复探测状态 |
| 完全降级 | 主+备均不可用 | 返回本地降级服务（基础查询+省钱建议） |

| Key | 类型 | 说明 | TTL |
